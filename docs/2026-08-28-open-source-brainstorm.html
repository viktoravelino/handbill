tot, us, and the gap

tot is a hosted service. npm i -g @plannotator/tot, run tot notes.md, get https://tot.page/aB3xK9q. Its pitch is git-backed publishing: the link is a living branch tip that moves on tot update, and every publish also mints a frozen @hash snapshot. No accounts; the link is the key, so anyone holding it can also update or delete the page. The CLI (~6 source files, one dependency, ~/.tot registry) is MIT. The backend is Plannotator’s closed Workspaces platform on Cloudflare Artifacts — the repo’s own docs/SPEC.md says “tot is a thin CLI over /v1”. You cannot run tot yourself.

What we have is the opposite shape. A ~150-line Worker and an R2 bucket you own, on your own domain, with a bearer token for writes and content-addressed immutable URLs for reads. Plus a skill so agents publish without being told how. Everything is already in two small TypeScript files — it just has your domain hard-coded and lives in two private repos.

The gap tot leaves open is exactly the thing we have: the whole stack, self-hostable, in five minutes. That is the project.

Positioning

One line for the README:

Hand someone a page. One command turns a self-contained HTML file into an unguessable link on your domain — a Worker and a bucket you deploy once and own forever.

Four principles that decide every feature question below:

  1. You own it. Your Cloudflare account, your domain, your R2 bucket, your token. No hosted tier, no sign-up, no telemetry, nothing that phones home. If this project disappears, your links keep working.
  2. Immutable by construction. The URL is the content hash. The same bytes always land on the same URL; different bytes are a different URL. No living links in v1 — see aliases for how they come later without breaking this.
  3. Agent-native. The reason this exists is that agents finish work by handing you a link. The repo ships the skill, not just the CLI. Humans get a nice CLI as a side effect.
  4. Small enough to read. One Worker file, one CLI file, zero runtime dependencies. If the Worker needs a framework, the feature is wrong.

Who it is for: people running coding agents (Claude Code, Codex, Cursor) who want plans and reports as links; solo devs who already have a domain on Cloudflare; anyone who read tot’s README and thought “nice, but I want it on my own domain.”

Architecture

Three deliverables in one repo, each independently useful. The Worker is what you deploy, the CLI is what you install, the skill is what your agent reads.

Worker

Keep it as it is, with one change: ZONE stops being a constant and comes from env.ZONE (a vars entry in wrangler.jsonc). classifyHost takes the zone as an argument so tests stay pure. Everything else — content hashing, hash-mismatch rejection, immutable cache headers, noindex, server-side list, the 5 MB cap — is already right for the general case.

The self-host story is three edits in wrangler.jsonc (zone_name, the two routes, ZONE), one wrangler secret put PUBLISH_TOKEN, and two DNS records (* and api, proxied). Cloudflare’s Deploy to Cloudflare button reads wrangler.jsonc and provisions the Worker and the R2 bucket from a repo URL; the custom-domain routes and the secret remain manual, which the docs walk through. Free tier covers it many times over.

CLI

Port publish.ts from Bun-only APIs to Node-compatible ones (node:crypto, node:fs/promises, global fetch) so npm i -g handbill works for everyone; it still runs under bun. Still zero dependencies.

The CLI prints exactly one line on success, the URL, and nothing else on stdout. That is the contract that makes it composable for agents and shell scripts alike. Errors go to stderr with a non-zero exit.

Skill

The current SKILL.md already has the right content: when to publish, what not to publish, list, unpublish, how to debug. It loses the embedded publish.ts and calls handbill instead. Your agents-config copy becomes a symlink to (or a vendored copy of) skills/handbill/ in the repo, so the two never drift.

Your own deployment

Nothing has to move. The Worker named publish-plan and the bucket keep running; the repo’s wrangler.jsonc can ship with your zone as the worked example (a zone name is public information, not a secret) and a comment saying “change these three lines”. When you eventually want the Worker to be called handbill, deploy a second Worker bound to the same bucket, move the routes, delete the old one — no data moves.

Product decisions

Proposed, not made. Each one is a place tot chose differently, so it is worth being explicit.

  1. Immutable, content-addressed URLs only in v1. tot’s living link is its headline feature; ours is that a link can never change under a reader. Living links come later as aliases (below), opt-in, without touching the hash model.
  2. Writes need a token. tot lets anyone with the link update or delete the page. That is fine for a throwaway; it is wrong for a plan you sent to your team. One deployment, one token, kept in the config file or env.
  3. One self-contained HTML file per page. tot scans HTML for local assets and uploads them (parse5, a workspace per page). We refuse anything that is not one file, and the CLI tells you which local refs would 404. Inlining local assets into the file is a possible later step; multi-object pages are not.
  4. No markdown in v1. Agents already emit HTML. Markdown is the most requested thing v1 will not have, so it is first on the roadmap, done as render to a self-contained HTML with a built-in stylesheet in the CLI — the Worker never learns about markdown.
  5. Server-side list. tot keeps a local ~/.tot registry because anonymous pages have no owner. We have a token, so the bucket is the truth and any machine with the token sees the same list.
  6. The 12-hex hostname stays. 48 bits is unguessable and short enough to read out loud. A hostname per page also gives each document its own origin: one page’s JavaScript cannot touch another’s storage.
  7. Cloudflare only. No adapter layer for S3/Vercel/Deno. The whole value is “one config file and it runs”; a second backend doubles the surface for a user who does not exist yet.
  8. No accounts, no hosted tier, ever. The moment there is a handbill.dev you can publish to, it is tot with worse marketing. The project is the self-host kit.

Bold ideas and roadmap

None of these are v1. They are listed so v1 does not accidentally close the door on them.

  • v1.1Aliases: living links without breaking hashes. handbill alias plan a3f9c1d4e2b8 writes plan → a3f9c1d4e2b8 to a KV namespace; plan.viktoravelino.dev serves (not redirects to) the current hash with max-age=60. The rule is trivial: a first label that is not 12-hex is looked up in KV. Guessable by design, so it is opt-in per name. This is tot’s branch/commit model with one KV lookup instead of a git platform.
  • v1.1Markdown in the CLI. handbill notes.md renders to a self-contained HTML with a small built-in stylesheet (light/dark, ~2 KB) and publishes that. One dependency (a markdown parser) in the CLI, zero in the Worker.
  • v1.2Inline instead of upload. Where tot uploads a page’s local images/CSS/JS as separate objects, the CLI can inline them (data URIs, <style>, <script>) so the server still stores one object. Keeps the Worker single-object forever.
  • v2Encrypted pages: a private mode even the host cannot read. handbill --private plan.html encrypts client-side, uploads ciphertext wrapped in a ~1 KB bootstrap page, and puts the key in the URL fragment (#k=…), which browsers never send to the server. The Worker stores bytes it cannot read. tot explicitly has no private mode; this would be the first self-host pastebin-style page host with one. Real complexity; do it only if people ask.
  • v2Expiry. --ttl 7d writes an expiresAt metadata field; a cron trigger sweeps. R2 lifecycle rules are bucket-wide, so per-page TTL needs the sweep.
  • neverAnalytics, view counts, comments, custom themes, a dashboard. Each one is a reason to run a server that knows about users. The bucket list is the dashboard.

Build order

Roughly a weekend if done in this order. Each step ends with something that works on its own.

  1. Step 01 · 1h

    Name and repo

    Actions

    • Pick the name; optionally register the .dev.
    • Create github.com/viktoravelino/<name>. Move ~/projects/publish-plan in with history (git mv the Worker into worker/, add the workspace package.json). Keep plans/ out of the public repo or move them to a private notes folder.
    • MIT license, .gitignore already covers .env and .wrangler.

    Done when

    bun test passes from the repo root and the public repo contains no token, no plan, no .env.

  2. Step 02 · 2h

    Generalise the Worker

    Actions

    • ZONE from env.ZONE; classifyHost(hostname, zone); tests updated.
    • wrangler.jsonc with your zone as the example and a top comment marking the three lines to change. Add "vars": { "ZONE": "viktoravelino.dev" }.
    • Fail loudly at request time if ZONE or PUBLISH_TOKEN is missing (the API already fails closed on the token).
    • docs/SELF-HOSTING.md: account, DNS (* + api, proxied), Universal SSL wildcard note, secret, deploy, the curl that proves it.

    Done when

    Redeploying to your account changes nothing observable, and a fresh account following only the doc gets a working page.

  3. Step 03 · 3h

    The CLI as an npm package

    Actions

    • cli/src/api.ts: hashOf, publish, list, remove over fetch; Node and Bun compatible; typed responses inferred from one Page type.
    • cli/src/cli.ts: parseArgs, config resolution (env > config file), stdin via -, --open, --endpoint. One URL on stdout, errors on stderr.
    • Tests: hashing, config precedence, one mocked round-trip per command. No smoke tests.
    • Build with bun build --target=node to a single dist/cli.js with a shebang; files: ["dist"].

    Done when

    npm i -g ./cli on a machine without bun publishes a page to your deployment.

  4. Step 04 · 1h

    Skill and your own setup

    Actions

    • skills/handbill/SKILL.md: today’s text, calling handbill. Frontmatter compatible with Claude Code and Codex.
    • agents-config: replace the vendored skill with a symlink or a copy step in install.sh. Migrate ~/.config/publish/token to ~/.config/handbill/config.json.
    • Update the memory file so future sessions use handbill, not publish.ts.

    Done when

    An agent asked to “give me a link” ends with a URL, using the installed npm CLI.

  5. Step 05 · 2h

    README, CI, release

    Actions

    • README: one-line pitch, a terminal recording (handbill plan.html → URL → the page), the Deploy button, the 5-minute self-host, the comparison table, the security note (“the link is public, the token is yours”).
    • SECURITY.md with a contact; the threat model in three sentences.
    • CI: typecheck + test on push; npm publish --provenance on tag.
    • Publish 0.1.0.

    Done when

    npx handbill --help works for a stranger and the README answers “why not tot?” without being asked.

Launch checklist

  • A 20-second recording: agent finishes a plan, prints a link, the link opens on a phone.
  • Post where the audience is: the Claude Code and Codex communities, the thread where Theo shared the plan-as-HTML idea, Hacker News as “Show HN: self-hosted tot.page in one Worker”.
  • Open a friendly issue on tot linking to it as the self-host option — different tool, same idea, no competition.
  • A good first issue for markdown rendering, since it is the first thing people will ask for.
  • Keep the dependency count at zero on the README badge line; it is the argument.

Decisions you need to make

  • namehandbill, plaque, or something else? And buy the .dev now or not?
  • scopeImmutable-only v1 (recommended) or ship aliases in v1 to match tot’s headline feature?
  • scopeMarkdown at v1 or v1.1? It adds the first dependency and a stylesheet to maintain, but it doubles who cares.
  • repoMove publish-plan with its history, or start clean and copy the Worker over? History shows the design was deliberate; a clean start is tidier.
  • runtimeNode-compatible CLI (recommended, wider install base) or stay Bun-only and keep the current file nearly as-is?
  • privacyShip your zone as the worked example in wrangler.jsonc, or placeholders? The zone is public anyway; the example is friendlier.

Assumptions in this document: Cloudflare stays the only target; the existing URL shape and API contract are kept verbatim; the project stays a self-host kit with no hosted offering.
