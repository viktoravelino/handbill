PRD · versions · implementation plan · 2026-08-28

handbill

Hand someone a page. One command turns a self-contained HTML file into an unguessable, immutable link on a domain you own. Self-host first; a hosted tier later, from the same code. This document is the product definition, the user stories per version, the technical design on Effect, and the build order for ~/projects/handbill, a fresh repo.

Product

Problem. Coding agents finish work by producing documents — plans, reviews, reports — as HTML files on disk. Sharing one means attaching a file. The hosted services that take a page instead put it on someone else’s domain, hand edit and delete rights to anyone holding the link, and cannot be run on an account you own.

Product. handbill plan.html prints https://a3f9c1d4e2b8.yourdomain.dev. The URL is the content hash, so it never changes under a reader; a new version is a new link. Publishing needs a token; reading needs only the link. The whole stack — Worker, CLI, agent skill, docs — is MIT and deploys to your own Cloudflare account in minutes. Later, the same Worker runs in accounts mode on handbill.dev for people without a domain.

Goals

  • Time from “I have a domain on Cloudflare” to first published link: under 10 minutes, following the README only.
  • An agent with the skill installed ends a task with a working link, first try, without being told how.
  • The Worker stays small enough to read in one sitting; the CLI is one binary-like file with predictable stdout.
  • Hosted mode is a configuration of the same code, not a fork.

Non-goals

  • A site builder: no multi-file sites, directories, routing, build steps, or transforms on the server.
  • Collaboration: no comments, reactions, analytics, view counts, dashboards beyond a list.
  • Other clouds: Cloudflare is the only target. The value is one config file that works.
  • Editing in place. A link is a specific set of bytes, forever. Aliases (v0.2) are the escape hatch.

Success measures

  • The maintainer’s daily flow runs on handbill and the old publish-plan deployment is retired (v0.1).
  • Zero security reports rated high or above; every page served with noindex and immutable caching.

User stories

Acceptance criteria are the test list. Stories are numbered by the version they belong to.

v0.1 · Print

  • S1.1 · Ada

    As an agent operator, I want handbill plan.html to print one URL so that an agent’s last line is the deliverable.

    • stdout is exactly the URL followed by a newline; nothing else on stdout, ever.
    • Publishing the same bytes twice prints the same URL and stores nothing new.
    • Exit code 0 on success, non-zero with a one-line stderr reason otherwise.
  • S1.2 · Ada

    As an agent, I want to publish from stdin (handbill -) so that I never have to write a temp file.

    • Bytes are hashed and sent as-is; the 5 MB cap applies before upload.
  • S1.3 · Ada

    As an agent, I want --json on every command so that I can read { url, hash, created } without parsing prose.

    • Errors under --json are { error, message } on stderr, same exit codes.
  • S1.4 · Ada

    As an operator, I want handbill list to show what is published, newest first, with titles, so that I can find a link I lost.

    • Server-side list; every machine with the token sees the same thing.
    • Columns: url, date, title (from <title>, or “(untitled)”).
  • S1.5 · Ada

    As an operator, I want handbill remove <url|hash> to be idempotent so that unpublishing a mistake is one command with no questions.

    • 204 whether or not the page existed; the served URL returns 404 within seconds.
  • S1.6 · Sam

    As a self-hoster, I want to deploy from the README in under ten minutes so that I own my links.

    • Three edits in wrangler.jsonc (zone, two routes), one wrangler secret put, two DNS records.
    • A “Deploy to Cloudflare” button provisions Worker + bucket; the doc covers the remaining manual steps.
    • Free tier by default; the doc states the limits.
  • S1.7 · Sam

    As a self-hoster, I want handbill doctor to tell me what is wrong so that setup failures are not a mystery.

    • Checks: config file present, token present, endpoint reachable (GET /v1/health), token accepted, wildcard TLS valid for a probe hostname.
    • Each check prints pass/fail and one sentence of what to do.
  • S1.8 · Ada

    As an operator, I want the skill installable into Claude Code and Codex so that agents publish without instruction.

    • skills/handbill/SKILL.md in the repo; installable by copying or with a skills installer.
    • The skill says what not to publish (secrets, customer data) and how to unpublish.
  • S1.9 · reader

    As a reader, I want the page to load fast and never change so that a link I was sent is what was sent.

    • Cache-Control: public, max-age=31536000, immutable; X-Robots-Tag: noindex, nofollow; text/html; charset=utf-8.
    • Every path on a hash hostname serves the same document; the apex and unknown hosts return a small 404.
  • S1.10 · Rae

    As a contributor, I want tests that run with bun test and no Cloudflare account so that I can change the Worker safely.

    • An in-memory storage layer replaces R2 in tests; the CLI client is tested against the Worker handler in-process.

v0.2 · Words and names

  • S2.1 · Ada

    As a writer, I want handbill notes.md to publish a readable page so that markdown is a first-class input.

    • The CLI renders to a self-contained HTML with a built-in light/dark stylesheet; the Worker never sees markdown.
    • <title> comes from the first H1 or the filename.
  • S2.2 · Ada

    As an operator, I want handbill alias plan <hash|url> so that plan.mydomain.dev always shows the latest version while old hashes stay valid.

    • A first label that is not 12-hex is looked up in KV and served (not redirected) with max-age=60.
    • Aliases are guessable by construction; the docs say so and the feature is off until a KV binding exists.
    • alias remove, alias list.
  • S2.3 · Sam

    As a self-hoster, I want /v1/openapi.json and a docs page so that I can script against my own instance.

  • S2.4 · Ada

    As a human, I want --open and shell completions so that the CLI feels finished.

  • S2.5 · Sam

    As a visitor, I want handbill.dev to explain the project and link to the docs so that I can decide in one minute.

v0.3 · Hosted

  • S3.1 · Kai

    As someone without a domain, I want npx handbill plan.html to work after a login so that I get a link with no infrastructure.

    • handbill login opens a browser, mints an API key, stores it in the config file.
    • Default endpoint becomes https://api.handbill.dev; self-hosters keep overriding it.
  • S3.2 · Kai

    As a hosted user, I want list and remove to see only my pages.

    • Objects carry owner; a per-owner index backs list; remove requires owner match.
  • S3.3 · operator

    As the operator, I want quotas, rate limits, and a takedown command so that hosting strangers is survivable.

    • Per key: pages/day and total bytes; per IP: WAF rules on publish and read.
    • handbill admin takedown <hash> with an operator token; abuse contact and ToS published.

v0.4 · Sheets and time

  • S4.1 · Ada

    As a writer, I want local images, CSS, and scripts inlined at publish so that a page with assets is still one object.

  • S4.2 · Ada

    As an operator, I want --ttl 7d so that throwaway pages clean themselves up.

Technical design

Effect 4 end to end. The reason is not fashion: the two things this product needs to swap later — the auth strategy and the storage backend — are exactly what Effect’s services and layers are for, and the API contract as a typed value gives the CLI a client, the docs an OpenAPI spec, and the tests an in-process server, all from one definition.

Runtime decisions

  1. Effect 4.0.0-rc, pinned exact. v3 is feature-frozen and v4 is at release candidate with a unified version across the ecosystem. Everything we use lives in effect/unstable/httpapi, effect/unstable/http, and effect/unstable/cli. The unstable path means minor-version API churn until stable; pinning and a small surface make that a one-afternoon migration when it comes.
  2. Worker = HttpRouter.toWebHandler(appLayer). The Workers fetch handler classifies the hostname, then hands API requests to the Effect web handler and page requests to a small Effect that reads storage. No framework besides Effect.
  3. Contract is a package. packages/contract exports the HttpApi definition and schemas. The Worker implements it with HttpApiBuilder; the CLI consumes it with HttpApiClient.make; OpenApi.fromApi generates the spec. Nobody hand-writes a fetch or a status code.
  4. CLI = effect/unstable/cli on @effect/platform-node. Runs under Node ≥ 22 and bun. Bundled with bun build --target=node into one dist/cli.js; the published package has two runtime dependencies (effect, and marked since 0.2 rendered markdown) and one file. Help, completions, and prompts come free.
  5. Web = Astro + Starlight, static, on Workers static assets. Landing and docs only, from v0.2. A hosted-mode dashboard (v0.3) starts as an Astro page with one island; if it ever needs routing and auth state, TanStack Start. Not decided until it hurts.
  6. bun workspaces, oxlint + oxfmt, bun test. One package manager, one lint/format tool, no config sprawl.

Services and layers

What this buys concretely: the v0.3 hosted tier is Layer.provide(AuthAccounts) instead of AuthSecret, selected by a MODE var. Tests provide StorageMemory and call the same web handler with a new Request(…). The CLI’s integration test points HttpApiClient at that in-process handler — a full round-trip with no network and no Miniflare.

Hashing and identity

  • hash = hex(sha256(bytes))[0:12], computed by the client to form the URL and re-computed by the server to reject forgeries. 48 bits: unguessable, short enough to say out loud.
  • Objects carry customMetadata: { owner, title, publishedAt } from v0.1, even though owner is always "self" in secret mode. That single field is what makes v0.3 additive.
  • Hosted mode open question: identical bytes from two owners. Options are first-owner-wins (documented) or salting the hash with the owner id in accounts mode. Decide at v0.3; nothing in v0.1 forecloses either.

Implementation plan · v0.1

Ordered so every milestone leaves something that runs. Estimates are focused hours, agent-assisted. Milestones 3 and 4 can run in parallel once the contract (milestone 2) exists; file ownership is by app directory so they never collide.

  1. M1 · 1h

    Scaffold

    Tasks

    • git init, bun workspaces, base tsconfig (strict, exactOptionalPropertyTypes, noUncheckedIndexedAccess), oxlint/oxfmt, MIT, .gitignore (.env, .wrangler, node_modules, dist).
    • Empty packages with package.json and a passing placeholder test each so CI is green from commit one.
    • CI: bun install --frozen-lockfile, typecheck, lint, test.

    Done when

    CI green on the first push; bun run typecheck and bun test pass at the root.

  2. M2 · 2h

    Contract

    Tasks

    • Hash schema (12 lowercase hex, branded), Page, PublishResult, the four tagged errors with status annotations.
    • HttpApi with groups pages (publish, list, remove) and meta (health); bearer security on pages.
    • Raw-body publish endpoint: verify HttpApiSchema binary encoding on a spike; fall back to reading HttpServerRequest in the handler if it fights us.
    • Test: OpenApi.fromApi produces a spec with the four error responses.

    Done when

    The contract package typechecks and the spec snapshot test passes. This is the interface the next two milestones build against.

  3. M3 · 4h

    Worker

    Tasks

    • Services: Storage (R2 + memory layers), Auth (secret layer), Config from env.
    • HttpApiBuilder.group handlers for pages and meta; HttpRouter.toWebHandler; hostname classifier; page serving with the immutable headers; 404 page.
    • wrangler.jsonc with the three marked lines, vars.ZONE, R2 binding, workers_dev: false.
    • Tests on the memory layer: hash mismatch, size cap, idempotent put, list order, delete idempotency, host classification table, headers.
    • Bundle-size check in CI (wrangler deploy --dry-run --outdir, fail above 1 MB gzip).

    Done when

    Deployed to the maintainer’s account as a second Worker on the existing bucket; the old publish script still works against it (contract compatibility proven), then routes move.

  4. M4 · 4h

    CLI

    • Config resolution (flag > env > file); HttpApiClient.make with a bearer transformer; hashing with node:crypto.
    • Commands: default publish (file or -), list, remove, doctor, completions; --json; stdout discipline.
    • Tests: config precedence, hashing, and one in-process round-trip per command against the Worker handler on the memory layer.
    • Build: bun build --target=node → dist/cli.js with shebang; files: ["dist"]; engines.node >= 22.

    Done when

    npm i -g ./apps/cli on a bun-less machine publishes, lists, and removes against the maintainer’s deployment.

  5. M5 · 1h

    Skill and migration

    Tasks

    • skills/handbill/SKILL.md for Claude Code and Codex, calling the installed CLI.
    • agents-config: replace the vendored publish-plan skill with a copy step; migrate the token to ~/.config/handbill/config.json; update the memory note.
    • Retire the publish-plan Worker once routes point at the new one.

    Done when

    “Give me a link” in a fresh Claude Code session ends with a working URL via handbill.

  6. M6 · 2h

    npx handbill --help works for a stranger; the README’s five steps reach a published link.

Status · what shipped, what changed

As of 2026-09-01. Where the build departed from the plan above, the departure and its reason are here so the plan stays readable as a plan.

  • 0.1 shipped 2026-08-28 as handbill@0.1.0 and 0.1.1; the maintainer’s flow is migrated and publish-plan retired.
  • Publishing is npm trusted publishing (OIDC) from release.yml, with provenance; no npm token anywhere. scripts/release.sh bump | tag is the two-move release, and it has a real dry run.
  • Nightlies, not in the plan. Every night at 05:00 UTC, and on demand, main is published under the nightly dist-tag as <release>-nightly.<UTC date-time>.g<sha>, skipped when main has not moved; latest and next are never touched. <release> is the version main is heading toward: a -dev version in apps/cli/package.json (0.2.0-dev → 0.2.0-nightly…) names it, and a plain release version means the next patch. A -dev version can never be tagged. A merged feature is installable the next morning instead of at the next release.
  • Worker budget is 1310 source lines, not the “~400” first written here: tests excluded, enforced by the CI size job, and services.ts split into config / storage / auth / aliases (and, in 0.3, quotas). It was 750 through 0.2, raised to 1125 in #88 because hosted mode earns it, and raised again in #116 because #88 had priced services that did not exist yet: M13 and M14 alone spent 390 of the ~315 it had allowed for all of 0.3. 0.3 ends at 1308 of 1310.
  • Shell completions shipped in 0.1 (M4), a version early. The descriptor is written by hand because the framework keeps its conversion internal; a test pins it to the real command tree.
  • Markdown (0.2). Parser is marked, chosen on bundle size (57 KB, no transitive dependencies, versus 195 KB / 209 KB for the alternatives) and kept as a real dependency rather than inlined. Title from the first H1 with inline markup resolved, else the filename; --markdown is how stdin opts in. Raw HTML in the source passes through unchanged — right for a self-hoster publishing to their own zone, revisited at 0.3 when hosted mode began serving strangers, and kept (see Open questions).
  • OpenAPI + /docs (0.2). The spec comes from HttpApiBuilder.layer(…, { openapiPath }), token-free and cached five minutes. The docs page is nine lines of hand-written HTML loading a pinned Scalar from a CDN — HttpApiScalar would have inlined Scalar’s 3 MB browser build and blown the 1 MiB gzip gate.
  • Aliases (0.2). AliasesKV when the ALIASES binding exists, AliasesDisabled when it does not, chosen in index.ts; the handlers never ask. Names are one DNS label that is not a hash and not api; the page is served at the name, never redirected, with max-age=60. Without the binding the routes answer 404 and the docs say why the feature is off by default: names are guessable.
  • Deferred from 0.1 to 0.3, recorded on the milestone: no separate Index service yet (list walks the bucket inside StorageR2), remove does not check owner (one owner in secret mode), request logging left to Cloudflare.
  • Alias commands and --open (0.2). handbill alias <name> <url|hash>, alias list, alias remove; a deployment without the binding gets one sentence naming it. --open goes through a Browser service the tests replace, so stdout stays one line and no test opens a window. list and remove are subcommands, so a page cannot carry those two names.
  • The site (0.2, live). apps/web is Astro + Starlight on handbill.dev, deployed from main as a second, assets-only Worker on the apex route. It has no content of its own: the landing page is README.md, the docs section is the repository’s own markdown files, and the CLI reference is generated from handbill --help before every build — so the site cannot drift from the code.
  • 0.2 shipped 2026-08-31 as handbill@0.2.0.
  • 0.3 shipped 2026-09-01 as handbill@0.3.0. Accounts mode has been live on handbill.dev since 2026-09-01: AuthAccounts + IndexKV + quota counters, all in one ACCOUNTS namespace; handbill login on GitHub’s device flow; handbill admin takedown behind its own ADMIN_TOKEN; the WAF rate limit, the terms and the abuse address on the site; the CLI’s default endpoint flipped to api.handbill.dev. Two of the three 0.1 deferrals closed here — Index is its own service and remove checks owner; request logging is still Cloudflare’s, deliberately.
  • The mode is the binding, not a var (0.3). The outline said MODE=accounts; what shipped picks AuthAccounts / IndexKV / QuotaKV when the ACCOUNTS binding exists and the secret-mode layers when it does not, decided once in index.ts — the rule aliases already followed. One consequence is the whole backout plan: unbind and deploy, and the Worker is on PUBLISH_TOKEN again with every page still serving and the namespace untouched.
  • No GET /v1/me, and no key-minting page (0.3). Both were in the 0.3 row and neither was built. handbill list already answers “what do I have”, and the quota numbers are two rows on the hosted page rather than a route nobody reads; sign-in is GitHub’s device flow in the terminal, so the site has no login, no session and no cookie. That also answers the framework question below without spending it.
  • Quotas are a ceiling, and they lean on the WAF (0.3). 25 pages a day and 250 MB per owner, counted in KV, which is eventually consistent — so parallel publishes overshoot by whatever rate the caller can sustain, and the per-IP rate-limiting rule is what bounds that rate. It is required rather than recommended before a zone hosts strangers. Exact counters would mean Durable Objects, which 0.3 deliberately does not have. The rules and the abuse runbook are configuration, so they live in docs/WAF.md rather than in code.
  • The drill is a document (0.3). docs/DRILL.md: the stranger test, the report→takedown→revoke loop, the quota 429, and the kill-switch rehearsal, each with the commands verbatim and a blank Result:/Time: slot. Run 1 is pending: the script merged first so it could be executed against main, and the numbers land in a follow-up commit. Findings become issues rather than inline fixes. It is not on the site — it is for whoever runs a deployment, not for whoever reads about one.
  • The three-self-hoster exit criterion is dropped, from 0.1’s and 0.2’s exit criteria and from the success measures. It measured adoption, not the product: nothing the project can do makes three strangers deploy on a schedule, so it could only ever hold a release hostage to luck. What it was really asking — that the README works end to end — is covered by the criteria that remain.
  • @handbill/contract stays unpublished until 1.0. Decided 2026-08-31, as the PRD leaned. Every deployment already serves /v1/openapi.json generated from that same contract, so anyone wanting a client can generate one against the instance they are actually talking to. Publishing now would put an Effect 4 release candidate in a package’s public types and make its churn a breaking change for other people; the 1.0 freeze is the honest moment.

Risks

  • effectv4 RC churn. unstable/* APIs may rename before stable. Mitigation: exact pin, small surface (one HttpApi, one router, one CLI command tree), and the contract package as the only place that touches the API-definition side.
  • effectRaw binary request body in HttpApi. The publish endpoint takes bytes, not JSON. Spike it in M2; the fallback (read the request stream in the handler) costs nothing in the contract.
  • workersBundle size and cold start. Effect 4 is markedly smaller than 3 (~20 KB minimal), but HttpApi and Schema add up. The CI size gate keeps it honest; Workers free allows 3 MB compressed.
  • peopleLearning curve for contributors. Effect is a barrier for a drive-by fix. Mitigation: the Worker source stays under 1125 lines (src/*.ts excluding tests, enforced by the size job), each service is one file, and the README links a “how this codebase uses Effect” page.
  • hostedBeing a host. Abuse, cost, liability. Contained by the separate account, quotas, rate limits, takedown, and by not doing it until 0.3.
  • scopeFeature pull toward a site builder. Every “can it also serve my folder” request is answered by the non-goals. Inlining (0.4) is the last concession.

Open questions

  • Hosted identical-bytes rule: first-owner-wins or owner-salted hash? Decided 2026-09-01: first-owner-wins (architecture decision 05). The second publisher gets the same URL, no index entry and no ownership — salting would have made the same bytes two addresses and broken “the URL is the content”.
  • Should @handbill/contract be public from 0.2 so people can write clients, or wait for the 1.0 freeze? Decided 2026-08-31: wait for 1.0 — see Status.
  • Markdown parser choice at 0.2 (size vs CommonMark fidelity). Decided 2026-08-29: marked, on size — see Status.
  • Raw HTML inside markdown: passed through today. Sanitize, keep, or only document it once hosted mode serves other people’s pages? Decided 2026-09-01: keep and document. Sanitizing markdown would be a half-measure while a whole HTML file — the main input — is served as given either way, so the terms say it plainly instead: nothing is rewritten, scanned or sanitised, and a page’s scripts are its publisher’s.
  • Does the hosted key-minting page justify a real app framework, or is one Astro island enough? Decided 2026-09-01: neither — there is no key-minting page. handbill login is GitHub’s device flow in the terminal, so the site kept no login, no session and no island.
