The paid tier

Payments land in 0.4, on Polar; 0.3 only makes room for them. This document fixes the shape — what "paid" means, what gets built, what has to exist outside the repo — and re-cuts the roadmap so "Sheets and time" moves to 0.5. It amends the 0.3 architecture (one new decision) and, once committed, the PRD's versions table.

  • Status §01 confirmed 2026-09-01; the rest is direction until 0.4 opens
  • Provider Polar (merchant of record)
  • Depends on 0.3 shipped and quiet for a few weeks
  • Exit upgrade raises a quota with no human in the loop; lapse lowers it without breaking a link

01 · Decisions carried in

All four were reviewed with the 0.3 architecture and confirmed on 2026-09-01; the second of them is now decision 11 of that document. What follows them in this file is still direction, not a settled design.

  1. Payments are 0.4, not 0.3. The hosted front door stays free-with-quotas so the two-minute stranger test survives; money is asked for only when the free tier binds.
  2. The tier field ships in 0.3 — accepted into the 0.3 architecture as its decision 11: the key record becomes { owner, created, revoked?, tier: "free" } and the quota service reads limits from a per-tier table from day one. Cost now: a handful of lines in M13/M16. Cost of retrofitting later: a KV migration.
  3. Polar is the provider — merchant of record, so VAT/GST/sales tax is their problem; checkout on their domain, which keeps the no-cookies-on-handbill.dev rule (0.3 decision 07) untouched; subscription webhooks and a TypeScript SDK. Revisited only if their terms or pricing change materially before 0.4 opens.
  4. Payment state affects write quotas only. The read path never consults tier, payment, or subscription status. A lapsed card can never break a published link. This is 0.3's invariant §01 extended to money, and it is permanent.

02 · The model

Two tiers, one product. No metering, no seats, no add-ons — a flat subscription that buys bigger numbers:

Tiers (free column confirmed with 0.3; paid column placeholders until 0.4 opens)
Limitfreepaid
Pages per day25250
Stored bytes250 MB5 GB
Page size5 MB5 MB — unchanged; it is a format constraint, not a paywall
Price—single monthly price, annual discount; picked at 0.4 launch
  • What paid deliberately does not buy in 0.4: aliases (operator-only per 0.3 decision 08 — selling guessable names to strangers is a phishing product), custom domains, longer hashes, priority anything. Quota is the whole product until demand says otherwise.
  • Lapse semantics: subscription ends → tier returns to free at period end. If stored bytes then exceed the free quota, publishing is blocked until the owner deletes below it — nothing is auto-deleted, no link breaks, ever. The 429 says exactly this.
  • Refund/abuse interplay: takedown and revocation (0.3 §07) are independent of payment state; a paying abuser is still revoked, and Polar's refund is a dashboard action, not code.

03 · Structure

Five pieces, three of them outside the Worker:

Components
PieceWhereWhat it does
Product + pricePolar dashboardone subscription product; checkout link generated from it
Pricing pageapps/webstatic; states both tiers' numbers and links out to Polar checkout — no cookies, no scripts
Checkout + portalPolar's domainpayment, invoices, cancel/renew — none of it ours
POST /v1/billing/webhookapps/workerverifies Polar's signature; flips tier on the owner's key records
handbill accountapps/cliprints owner, tier, quota usage — the "did my upgrade land?" command

The joining key. Checkout must tell us which owner paid. The pricing page links to checkout with the owner's id (gh:<id>) attached as checkout metadata — Polar echoes metadata back in webhook events, so the webhook handler maps event → owner → tier flip without storing any Polar state beyond the subscription id on the owner record (for support lookups). The CLI can print the personalized checkout URL (handbill account --upgrade) so the flow works without ever visiting the site.

Flows, in prose. Upgrade: checkout completes → webhook (subscription became active) → tier: "paid" → next publish sees the bigger table. Lapse: webhook (subscription ended/revoked) → tier: "free" → write path shrinks, read path never knew. Webhook downtime: events are retried by Polar; until one lands, the user has paid but sits on free quota — handbill account shows the mismatch, and a manual handbill admin tier <owner> paid is the operator's override (also the support tool). Reconciliation stays human-scale on purpose.

Worker budget estimate: webhook route with signature verification ~50–70 lines, tier table ~10, admin tier override ~10. The #88 headroom decision should assume roughly +90 for 0.4 on top of 0.3's needs.
