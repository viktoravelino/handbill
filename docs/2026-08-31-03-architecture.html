Architecture · v0.3 hosted · 2026-08-31

Hosting strangers

0.3 turns the maintainer's deployment into a public service: accounts, handbill login, per-owner lists, quotas, takedown. This is the design M13 builds against — the eleven decisions in §10 were reviewed one by one and accepted on 2026-09-01, and §11's questions are answered in place. It refines the PRD's v0.3 row; where they disagree, this document is newer and the PRD gets amended.

01 · What does not change

Hosted mode is additive. These invariants hold before, during, and after 0.3, and any design below that would bend one is wrong:

  • Published links never change. A hash URL handed out under 0.2 serves the same bytes under 0.3, and a hosted user's links keep serving even if their key is revoked or the hosted tier is switched off. Takedown of a page is the only thing that kills a link, and that is deliberate, logged, and operator-only.
  • Self-hosters notice nothing. Secret mode (PUBLISH_TOKEN) is untouched; no new binding is required; wrangler.jsonc gains commented, opt-in blocks at most. The 0.1 five-step deploy still works verbatim.
  • The handlers never ask which mode is on. Per AGENTS.md: a binding that may be missing picks its layer in index.ts. Accounts is a layer choice (AuthSecret / AuthAccounts), not an if.
  • Serving is dumb. Pages are bytes from R2 with fixed headers (immutable, noindex, per-page origin). No per-request auth, no cookies, no personalization on the read path — the read path stays cacheable and boring.
  • The Worker budget stays a real number — #88 settled it at 1125 lines, raised once from 750 because hosted mode earns it. Everything below is designed to fit inside that, not to argue with it.
  • Tests run on memory layers. Accounts, index, and quotas each get a memory implementation; no Miniflare, no network.

02 · Shape: services and layers

Three new services, each with the same two-layer pattern the storage and aliases services already use. index.ts picks by binding presence:

Services and their layers
ServiceHosted layer (binding)Self-host layer (no binding)
AuthAuthAccounts (ACCOUNTS KV)AuthSecret — today's token equality
IndexIndexKV (ACCOUNTS KV, shared)IndexBucket — today's bucket listing
QuotaQuotaKV (ACCOUNTS KV, shared)QuotaUnlimited — no-op

One KV namespace, not three. Accounts, index entries, and quota counters are key-prefixed records in a single ACCOUNTS namespace (§04). One binding keeps wrangler.jsonc's opt-in story simple — uncomment one block to become a host — and keeps us inside Workers' binding and namespace hygiene. ALIASES stays separate: it exists independently of hosting.

Auth's interface changes from "is this token valid?" to "who is this?": it resolves a bearer token to an owner string. AuthSecret answers the operator constant; AuthAccounts answers gh:<id> (§03). owner then flows where it always flowed — into customMetadata — except now it means something. This is why the PRD stored owner from day one.

03 · Identity: login and keys

GitHub device flow (decision 01, accepted). handbill login prints a code and opens github.com/login/device; the user types the code; the CLI polls GitHub, receives a GitHub access token, and exchanges it once at POST /v1/keys. The Worker verifies the token against api.github.com/user (its only outbound call, on this route only), mints a handbill key, and returns it. The CLI stores the key in ~/.config/handbill/config.json and discards the GitHub token.

Why device flow over the alternatives considered:

  • No OAuth callback route in the Worker — the redirect dance is GitHub's problem, not ours. The Worker gains one route, not three, which matters when every route is charged against the line budget.
  • No session cookies on handbill.dev, ever. A web-based login would put an auth cookie on the same registrable domain that serves strangers' HTML — §06 explains why that is the one thing we must not do before a PSL entry exists.
  • No secrets in the CLI. A device-flow client id is public by design.
  • Spam friction for free. A GitHub account is the cheapest identity that still costs an abuser something, and owner = gh:<numeric id> survives username changes.
  • Rejected: email magic links (needs an email sender, invites throwaways), password accounts (never), Cloudflare Access (operator-only, wrong for the public).

Keys. hb_ + 32 random bytes, base64url — the prefix makes leaked keys greppable (and registrable with scanners later). The Worker stores only SHA-256(key); a stolen KV dump mints nothing. Shown once at login; handbill logout deletes locally and revokes server-side (DELETE /v1/keys/current). Keys do not expire in 0.3 — revocation exists, expiry is 0.4-if-ever.

New contract surface (all under /v1, bearer-authed unless noted)
RouteAuthDoes
POST /v1/keysGitHub token in bodyverifies with GitHub, mints a key, returns it once
DELETE /v1/keys/currentthe key itselfrevokes the presenting key; 204, idempotent
DELETE /v1/admin/pages/:hashoperator tokentakedown: removes object + index entry (§07)

Failure honesty: POST /v1/keys with a bad GitHub token is a plain 401; GitHub being down makes login fail loudly and publish keep working — the two paths share nothing.

04 · Data model

Everything hosted lives in the ACCOUNTS namespace under four prefixes. R2 stays the source of truth for pages; KV is derived state that can always be rebuilt from bucket metadata.

Amended by M16 (#118). The o: prefix is the owner→keys index #111's review asked for and #85 deferred here: a key record is filed under its own digest, so without it an operator holding gh:<id> from an abuse report has nothing to enumerate and nothing to revoke. It is a pointer, not a copy — the value is empty and the k: record stays the one description of a key — and revoke leaves it in place, so the prefix lists every key an owner has ever minted rather than only the live ones. The operator-facing commands are in docs/WAF.md.

  • List is prefix = i:<owner>:, sorted client-side by publishedAt — an owner's page count is quota-bounded (§05), so one KV list call suffices; no cursor gymnastics.
  • Remove reads the object's customMetadata.owner from R2 — not the index — and compares to the caller. Someone else's hash answers 404, not 403: existence is never disclosed to non-owners. Then delete object, delete index entry, decrement bytes.
  • Consistency rule: the bucket wins. KV is eventually consistent and a publish can crash between writes. Write order on publish: R2 object first, then index, then counters. A page in R2 without an index entry is invisible in list but served and removable — annoying, harmless. An index entry without an object serves 404 like any unknown hash. A reconcile pass is deliberately not built in 0.3; the rule is documented in the code instead.
  • Same bytes, two owners — the hash collides by design. Confirmed in review: the second publisher gets the same URL (it is content-addressed; the URL was already public knowledge), but no second index entry and no ownership change — first writer keeps owner. The second publisher's remove therefore 404s. Simple, immutable, slightly surprising; the alternative (per-owner copies) was rejected because it breaks the one-hash-one-object model. M14 builds exactly this.

05 · Quotas and rate limits

Two enforcement layers with different jobs: quotas (in the Worker, per key, about fairness and storage) and rate limits (in the WAF, per IP, about floods — they run before the Worker and cost nothing at 738 lines).

Confirmed numbers — vars with defaults, stated on the hosted page
LimitValueWhereOn breach
Page size5 MB (existing)WorkerTooLarge 413
Pages per key per day25Worker, q:*:d:*QuotaExceeded 429
Stored bytes per owner250 MBWorker, q:*:bytesQuotaExceeded 429
Publish + key-mint, per IP10 / minWAF rate rule429 at the edge
Reads, per IPhigh (≈300 / min)WAF rate rule429 at the edge; legit readers never see it

QuotaExceeded is the fifth contract error, a Schema.TaggedError with a 429 annotation like its four siblings, carrying which limit and when it resets. Counters are best-effort — KV races can let publish n+1 through occasionally; quotas are a cost ceiling, not a billing system, and the WAF catches actual floods. The daily counter's 48h TTL makes stale counters self-cleaning.

The WAF rules are configuration, not code: the runbook in docs/ (M16) records rule expressions and thresholds so they can be re-created on any zone. Free plan allows the rate-limiting rule this needs.

06 · Serving strangers' HTML

The product is "we serve arbitrary HTML from strangers on our domain." That sentence should scare us into exactly the right amount of architecture:

  • riskCookie scoping is the sharp edge. Every page gets its own origin (<hash>.handbill.dev), which isolates storage, scripts, and cookies between pages and from the API — except that any page can set a cookie with Domain=.handbill.dev, readable by the site and every other page. Until handbill.dev is on the Public Suffix List — no longer held to 1.0, but not ours to schedule either (§11) — the mitigation is architectural: nothing on the domain uses cookies. The site is static, analytics is cookieless, auth is bearer-only, login is device flow (§03). A poisoned domain cookie has nothing to poison. The rule outlives the listing: decision 07 keeps it standing either way.
  • riskPhishing is the expected abuse, not an edge case: unguessable URL + free HTTPS + a plausible domain is exactly what a phisher wants. noindex keeps pages out of search; quotas cap volume; the real answer is operational — fast takedown, key revocation, and the drill (§07). The hosted page and ToS state plainly that pages are the publisher's, and the abuse contact is findable from any page's URL structure (documented on the site, since the pages themselves are untouchable bytes).
  • riskHosted aliases would hand phishers login.handbill.dev. Accepted (decision 08): aliases stay operator-only in 0.3. Hosted users get hash URLs, full stop. Names for the public — reserved-word lists, squatting, transfer — is its own project and not this release.
  • heldEnumeration and collisions. 48 bits of content hash: guessing a live link is ~2⁴⁷ tries against a WAF; fine for "unguessable, not secret" (SECURITY.md's words). Deliberate collision against a specific page is birthday-hard at this size but not absurd forever; the server recomputing the hash means an attacker can only collide, never overwrite (first write wins, §04). Revisit width at 1.0, not now.
  • heldThe read path changes in no way. Same headers, same immutability, same 404 shape for unknown hosts. Hosted pages are indistinguishable from self-hosted ones by design — there is nothing extra to leak.

07 · Abuse operations

S3.3's machinery, kept small enough to actually be used at 2am:

  • Takedown — handbill admin takedown <hash|url> → DELETE /v1/admin/pages/:hash with the operator token (a separate secret, ADMIN_TOKEN, never a user key). Deletes object + index entry; the URL 404s within seconds (nothing caches past the edge cache, which the delete purges). Idempotent 204. The operator then decides separately whether the key dies too — takedown and revocation are two acts, because mistaken publishes deserve a lighter touch than phishing.
  • Revocation — flipping revoked on the key record. The user's pages keep serving (invariant §01); they just can't publish more. Revoking + taking down everything an owner published is the drill's worst case: list by owner prefix, takedown each.
  • What the operator can see, said plainly (this goes in the ToS, M17): every page's content and metadata, owner identity as a GitHub id, quota counters, and Workers logs. What is deliberately not kept: no per-reader logs beyond Cloudflare's standard analytics, no IP retention in our storage, no content scanning in 0.3 — review is reactive, on report.
  • Reports — one abuse address on the site and in the ToS, answered by a human, with the takedown SLA in plain words. Legal exposure (DMCA agent registration, jurisdiction) is a checklist item for M17, not an engineering artifact.
  • The drill (M18) proves the loop on production: publish as a hosted user → report it → takedown → revoke → confirm the 404 and the dead key → write the timings down. Abuse tooling that has never been exercised is decoration.

08 · Rollout and backout

  • Order matters: ToS + abuse page live (M17) before the CLI that defaults strangers onto the service ships (M15's release in 0.3.0). The Worker can run accounts mode quietly for weeks first — binding present, nobody defaulted to it — which is exactly how M13/M14 get verified on production without a launch.
  • The flip is client-side only. "Default endpoint becomes api.handbill.dev" is a CLI fallback when no endpoint is configured (S3.1); no server behavior changes on release day. Self-hosters have an endpoint configured, so the flip does not touch them.
  • Kill switch: remove the ACCOUNTS binding and deploy — the Worker reverts to secret mode, hosted publishing 401s, and every already-published page keeps serving, because serving never consulted accounts. Worst-case backout is one config line, and it strands no reader.
  • Blast radius note: hosted mode runs on the maintainer's existing zone and bucket. If drills reveal that mixing operator pages and stranger pages in one bucket is uncomfortable, a second bucket is a binding away — but that is a 0.4 refactor, not a 0.3 requirement.

09 · Cost envelope

Sanity check that abuse is bounded by money as well as rules, on Workers' paid plan ($5/mo, which the account is on for R2 anyway):

  • KV: a publish costs ~4 writes (object aside): index, two counters, occasionally a key read refresh. 1k writes/day is deep inside free allowances; KV reads on publish are negligible next to the free 10M/day.
  • R2: 250 MB × even 1,000 abusive accounts is 250 GB ≈ $3.75/mo storage worst case, and quotas cap the write rate at 25 × 5 MB/day/key. Egress is free — the scary cloud bill (bandwidth amplification) structurally does not exist on R2.
  • The WAF read limit caps request floods before they bill as Worker invocations.

Conclusion: the service cannot be made expensive quickly by one actor; it can be made annoying, which is what §07 is for.

10 · Decisions adopted here

Reviewed one by one and all accepted as written on 2026-09-01; decision 11 is carried in from the 0.4 paid tier document (docs/2026-08-31-04-paid.html), accepted with them. These are settled — reopening one means a new issue naming its replacement, not a re-read of this list:

  1. GitHub device flow is the login; owner is gh:<numeric id>; the Worker's only outbound call is verifying mints. (M13)
  2. Keys are hb_-prefixed, stored only as SHA-256, shown once, revocable, non-expiring. (M13)
  3. One ACCOUNTS KV namespace holds keys, index, and counters under prefixes; ALIASES stays separate. (M13/M14)
  4. The bucket wins over the index; write order R2 → index → counters; no reconcile job in 0.3. (M14)
  5. Cross-owner remove is 404, and on hash collision the first writer keeps ownership. (M14)
  6. Quota numbers: 25 pages/day, 250 MB/owner, WAF at 10/min publish and ≈300/min read per IP; QuotaExceeded 429 joins the contract. (M16)
  7. No cookies anywhere on handbill.dev until the PSL entry lands — this constrains every future site feature and is the price of hosted mode before 1.0. (standing)
  8. Aliases remain operator-only in 0.3. (scope)
  9. Takedown and revocation are separate acts; operator token is its own secret. (M16)
  10. M17 ships before the 0.3.0 release flips the default endpoint; backout is unbinding ACCOUNTS. (M18)
  11. The tier field ships in 0.3, payments in 0.4. The key record is { owner, created, revoked?, tier: "free" } and the quota service reads its limits from a per-tier table from day one; Polar, checkout and the billing webhook are 0.4's. The read path never checks payment state — §01's promise extended to money, permanently. (M13/M16)

11 · Questions, answered

Answered in the same review, 2026-09-01. Each was a real fork; none is open any longer.

  • PSL now instead of 1.0? — now, as far as it is ours to decide. Decided 2026-09-01: stop holding the submission back to 1.0, because the listing is free and takes weeks-to-months to propagate, and it closes §06's cookie edge. Submission prepared 2026-09-01, not filed — the list asks for a project serving thousands of distinct users, and 0.3 has not shipped, so filing today invites a decline on the merits. It goes in when hosted mode can answer that question with a number. Meanwhile nothing depends on it: the listing would change cookie behaviour for the site too (no cross-subdomain anything, ever), which decision 07 commits to regardless. The 1.0 row of the roadmap is the checkpoint, not the deadline.
  • Quota numbers — confirmed. 25 pages/day per key and 250 MB per owner ship as written; the paid multiples in 0.4 (250/day, 5 GB) stay placeholders until that version opens.
  • GitHub-only login — accepted. It makes GitHub a hard dependency of onboarding, never of publishing or reading: an outage blocks new keys and nothing else. Right for this audience; a second provider is a later version's problem, not a gap in this one.
  • Takedown transparency — a plain 404, no tombstone. A taken-down page is indistinguishable from a hash that never existed. Tombstones leak that something was there and invite argument on a page we no longer control.
  • Raw HTML inside markdown — kept, and documented. 0.2 deferred the sanitize-or-keep question to hosted mode; hosted mode answers it by making it moot, since a hosted user can publish arbitrary HTML directly and the markdown path is only a convenience on top. So passthrough stays, and it becomes a line in M17's words: what we render, we render as given.
  • Where does the mint page live if device flow ever feels clunky — a static page on the site could guide the flow without cookies, but adds words to maintain. Still not needed for v1 of login; the only item here left deliberately unanswered.
